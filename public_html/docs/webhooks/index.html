Webhooks, datasets, and profiling

Capture inbound webhooks, trigger collection runs from events, run datasets, and profile performance.

On this pageCapturing inbound webhooksWebhook-triggered collection runsData-driven (dataset) runsPerformance profiling

Not every test starts with you pressing Send. Spi can receive inbound HTTP callbacks, react to them by running a collection, iterate a collection over a dataset, and profile how a single request performs under load. Manage inbound endpoints in Webhooks.

Capturing inbound webhooks

Create a webhook endpoint and Spi gives you a public capture URL:

text
https://apispi.com/hook/{token}

Any HTTP method to that URL is captured. It is unauthenticated by design — the token is the credential, exactly like a Slack incoming-webhook URL — and it always answers quickly without revealing whether a token exists.

Inspecting captures

Each capture records the method, headers, query string, body, and source IP. A few safeguards apply:

  • Sensitive headers (authorization, cookie, x-api-key, proxy-authorization) are stored as a mask, never verbatim.
  • Bodies larger than 64 KB are truncated, not rejected, and flagged as truncated.
  • Old captures are trimmed so an endpoint keeps a rolling window.

Silence detection

An endpoint can expect a request at least every N minutes. If nothing arrives it goes silent and alerts you; when a request arrives again it reports the recovery — over the same alert channels your monitors use.

Webhook-triggered collection runs

An endpoint can be wired to trigger a collection run whenever it receives a request. This is event-driven testing: a provider's callback kicks off your suite. The run happens off the request path, so the provider still gets an immediate response.

Top-level scalar fields of a JSON payload are handed to the run as variables named webhook_<key> (plus webhook_method), so the suite can target the exact record the callback named. For a payload of {"order_id": 42}, the run can reference {{webhook_order_id}}.

Data-driven (dataset) runs

Instead of running a collection once, run it once per row of a dataset. Each row supplies a set of variables that override the environment for that iteration, so one collection covers many cases — different users, inputs, or edge cases — and you get a pass/fail per row.

Performance profiling

A saved request can be profiled by sending it repeatedly and summarising the timings — latency percentiles and throughput — so you can see how an endpoint behaves under repeated load, separate from correctness checks.

Triggered runs, dataset runs, and profiling are throttled like other outbound tests to protect both Spi and the targets you point them at.
