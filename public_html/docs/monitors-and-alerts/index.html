Monitors and alerts

Schedule a collection, track uptime, and get alerted when status changes.

On this pageSetting up a monitorAlert on transition, not on repeatAlert channelsMCP drift monitorsUptime and status

A monitor runs a collection on a schedule, records each run as a history point, and alerts you when its pass/fail status changes. It is how you turn a suite of checks into continuous confidence that an API is healthy. Manage monitors in Monitors.

Setting up a monitor

  1. Pick the collection to run and the environment to run it against.
  2. Choose how often it should run.
  3. Enable alerts and choose the channels to notify.

Each run is stored as an inspection report and a lightweight history entry (passed/failed, timing, and how many steps passed). Older history is trimmed automatically so a monitor keeps a rolling window rather than growing forever.

Alert on transition, not on repeat

Alerts fire only when the status changes — passing to failing, and failing back to passing. A monitor that emailed every five minutes while an API was down would get muted, and then it would not be a monitor any more. The first run establishes a baseline and does not announce an outage or a recovery.

Alert channels

Alerts go to your email plus any enabled alert channels. A channel is a reusable destination, shared across all your monitors. Supported channel types:

  • Slack — an incoming-webhook URL; the alert is posted as a message.
  • Discord — an incoming-webhook URL; the alert is posted as a message.
  • Webhook — a generic URL that receives a structured JSON payload describing the event.
Webhook, Slack, and Discord channels work with no SMTP configured at all, and one failing destination never stops the others. Channel URLs are credentials — anyone holding one can post to your channel — so they are treated as secrets.

MCP drift monitors

A monitor can instead watch an MCP server for drift: it snapshots the server's tool list and compares each run against the previous snapshot. When the surface changes it records a failing result and alerts once; the new shape then becomes the baseline, so it does not re-alert forever or send a misleading "recovered" message. See MCP testing.

Uptime and status

A monitor's history is the raw material for a public status page, which renders current status and recent uptime from these results at a shareable URL.
