Sending requests

The Tester in depth: protocols, headers, body, params, and reading responses.

On this pageChoosing a protocolWorked examples by protocolHeadersQuery paramsRequest bodyReading the response

The Tester is where you compose and send a single request over any supported protocol and inspect exactly what came back. This article covers each part of the request panel.

Choosing a protocol

The protocol selector changes what the rest of the panel offers. Spi supports these protocols directly:

  • REST — pick a method (GET, POST, PUT, PATCH, DELETE, and so on), set a URL, and optionally add headers, query params, and a body.
  • MCP — point at an MCP server endpoint (Streamable HTTP) and call its tools, prompts, and resources.
  • A2A — call an Agent-to-Agent endpoint, or fetch its agent-card.
  • gRPC — a unary call over HTTP/2. Describe the request message as a JSON array of fields, e.g. [{"field":1,"type":"string","value":"world"}]. Toggle TLS for HTTP/2 over TLS.
  • MQTT — publish or subscribe against a broker, with a topic and message.
  • AMQP — publish or consume against a broker, with a queue or exchange and a message.
There is no separate GraphQL or SOAP protocol: a GraphQL request is a REST POST with a JSON body ({"query": "..."}), and SOAP is a REST POST with an XML body and the appropriate content-type header.

Worked examples by protocol

Concrete values you can adapt. Replace the example hosts with your own, and prefer {{variables}} from an environment for anything secret.

REST — GET with query params

Fetch a filtered list. The query string can live in the URL or in query-param rows — both produce the same request.

http
GET https://api.example.com/v1/users?role=admin&limit=25
Authorization: Bearer {{token}}
Accept: application/json

REST — POST with a JSON body

Create a resource. Set Content-Type: application/json and put the JSON in the Body field.

http
POST https://api.example.com/v1/users
Authorization: Bearer {{token}}
Content-Type: application/json
json
{
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "role": "admin"
}

GraphQL — a REST POST

Send to your GraphQL endpoint as a POST. The body is a JSON object with a query and optional variables.

json
{
  "query": "query($id: ID!) { user(id: $id) { name email } }",
  "variables": { "id": "42" }
}

MCP — call a tool

Choose the MCP protocol, set the server URL, and pick a method such as tools/list or tools/call. Spi performs the initialize handshake for you. For tools/call, the params name the tool and its arguments:

json
{
  "name": "search_documents",
  "arguments": {
    "query": "quarterly revenue",
    "limit": 5
  }
}

Use tools/list with empty params ({}) to discover what a server exposes before calling anything.

A2A — send a message

Choose A2A and use agent-card to fetch an agent’s capabilities, or message/send to talk to it:

json
{
  "message": {
    "role": "user",
    "parts": [
      { "kind": "text", "text": "Summarise the latest incident report" }
    ]
  }
}

gRPC — a unary call

Set host (e.g. grpc.example.com), port (443 with TLS on), and service_method (e.g. helloworld.Greeter/SayHello). Describe the request message as an array of field descriptors — no .proto compilation needed:

json
[
  { "field": 1, "type": "string", "value": "world" }
]

MQTT — publish and subscribe

Set the broker host and port (1883, or 8883 for TLS), choose an action, and give a topic. To publish, add a message and QoS:

json
{
  "action": "publish",
  "topic": "sensors/kitchen/temperature",
  "message": "{\"celsius\": 21.4}",
  "qos": 1
}

To subscribe, give a topic filter (wildcards allowed) and bound the wait — Spi collects messages up to max_messages or until timeout:

json
{
  "action": "subscribe",
  "topic": "sensors/#",
  "max_messages": 5,
  "timeout": 10
}

AMQP — publish to a queue

Set the RabbitMQ host and port (5672, or 5671 for TLS), then publish a message to a queue or consume one with basic_get:

json
{
  "action": "publish",
  "queue": "jobs.email",
  "message": "{\"to\": \"ada@example.com\", \"template\": \"welcome\"}"
}

Headers

Add request headers as name/value rows. For gRPC these become call metadata. Header names and values can both contain {{variables}}.

http
Authorization: Bearer {{token}}
Content-Type: application/json

Query params

For REST requests, add query parameters as rows; Spi appends them to the URL. You can also type them directly into the URL — either works. These two are equivalent:

text
Rows:   status = active
        page   = 2

URL:    https://api.example.com/v1/orders?status=active&page=2

Values can use {{variables}}, e.g. api_key = {{api_key}}.

Request body

The body field is labelled to match the protocol — Body for REST, Request for gRPC, Message for MQTT and AMQP. For REST, send JSON, XML, form data, or plain text; set the matching Content-Type header.

A JSON body with a variable pulled from the active environment:

json
{
  "order_id": "{{order_id}}",
  "status": "shipped",
  "tracking": { "carrier": "DHL", "code": "JD0002" }
}

A form-encoded body (set Content-Type: application/x-www-form-urlencoded):

text
grant_type=client_credentials&client_id={{client_id}}&client_secret={{client_secret}}

Reading the response

Every response shows:

  • Status — the HTTP status code (or protocol-specific outcome).
  • Time — how long the request took, in milliseconds.
  • Headers — the response headers.
  • Body — the response payload, pretty-printed when it is JSON.

Requests you send are kept in your history so you can revisit them. When you are happy with a request, save it — saved requests can carry assertions and a response contract, and can be added to collections.

Spi guards outbound requests against SSRF, so requests to internal or loopback addresses may be refused. This protects the shared infrastructure the Tester runs on.
