Response snapshots

Capture a golden response and catch value-level drift by diffing later responses against it.

On this pageSnapshot vs contractCapturing a snapshotHow a response is diffedSnapshots in collections and monitors

A snapshot is a captured "golden" response — its status and its body — that Spi stores on a saved request and diffs later responses against, value by value. Where a response contract checks only the shape (types and required fields), a snapshot checks the actual values: it is regression testing at the leaf level, so a field that flips from 42 to 43, or an array that gained an element, is caught even though the shape never changed.

Snapshot vs contract

The two catch different kinds of drift, and they complement each other:

  • A response contract is schema-level — it records the type of each field and which are required, and fails on breaking shape changes. A value changing from 42 to 43 is invisible to it, because the type is still an integer.
  • A snapshot is value-level — it records the exact status and body, and fails when any value drifts. It is stricter, so use it when a response is meant to be stable.

Capturing a snapshot

Send the request in the Tester until you get the known-good response you want to lock in, then use the Snapshot panel on the saved request:

  • Capture — store the current response as the golden snapshot.
  • Recapture — replace the stored snapshot with a newer response once a change is intentional.
  • Clear — remove the snapshot so the request is no longer value-checked.

How a response is diffed

When a later response is compared against the snapshot, Spi walks both bodies and reports each difference at its leaf path:

  • Changed — a leaf whose value differs from the golden value, reported as the path with its before and after.
  • Added — a leaf present in the new response that the snapshot did not have.
  • Removed — a leaf the snapshot had that is gone from the new response.
  • Status change — the response status no longer matches the captured status.

Any drift at all fails the check — a snapshot is an exact match or nothing. A diff might read:

text
status            200 -> 200   ok
~ data.total      42  -> 43       changed
+ data.items[2]                 added
- data.cursor                   removed

Snapshots in collections and monitors

A snapshot travels with its saved request, so it is also checked when that request runs as a step in a collection. That in turn means a monitor running the collection on a schedule re-checks the snapshot on every run — so a value-level regression trips an alert the moment it appears, with no assertion written for it.

The golden body is stored server-side on the saved request and is never returned to the client — the panel shows only whether a snapshot exists and the diff of the latest run. Alongside assertions and response contracts, snapshots are the third drift signal: assertions check what you asserted, contracts check the shape, and snapshots check the values.
