Collections

Chain saved requests into ordered steps, thread variables between them, and run the lot.

On this pageSteps and orderingThe variable pool and extractionAssertions and contracts per stepContinue on failureRunning a collection

A collection is an ordered sequence of saved requests, run start to finish against one environment. It is how you model a real flow — log in, create a record, fetch it, delete it — and get a single pass/fail for the whole thing. Manage them in Collections.

Steps and ordering

Each step wraps a saved request. Steps run in order, top to bottom, so you can arrange them into a dependency chain. The request that each step sends is resolved against the current variable pool immediately before it is sent — which is what makes variable threading (below) work.

The variable pool and extraction

A run starts with the selected environment's variables as its pool. A step can then extract values from its response and add them to the pool, so a later step can use them. That is how a login step hands a token to every step after it.

An extraction rule is a name plus a path into the response — the same path forms assertions use: a dot path into the JSON body, or status, time_ms, or header.<name>. The value is stored under the name and becomes available as {{name}} in subsequent steps.

text
Step 1  POST /login       extract  token  <-  data.access_token
Step 2  GET  /me           header   Authorization: Bearer {{token}}
Only scalar values (strings, numbers, booleans) can be extracted, because only a scalar can be substituted back into a later request. A path that resolves to an object or array is skipped.

Assertions and contracts per step

Each step is evaluated with the assertions and response contract attached to its saved request. A step passes when the response is OK, its assertions all pass, and there is no breaking contract drift.

Continue on failure

By default a collection stops at the first failing step, and the remaining steps are reported as skipped rather than silently dropped. Turn on continue on failure to run every step regardless — useful for an independent suite of checks where one failure should not hide the others.

Running a collection

Run a collection from the UI and you get a full report: total, passed, failed, and skipped counts, the elapsed time, and per-step detail including the resolved URL (with secrets masked), status, timing, assertion results, contract drift, and which variables it extracted.

A collection with no steps is reported as a failure, not a pass — a monitor running an empty collection should not report green while checking nothing.

Collections can be run automatically by a monitor, triggered by an inbound webhook, run over a dataset, or run from CI over the programmatic API. They can also be exported to Postman or OpenAPI — see Reports and sharing.
