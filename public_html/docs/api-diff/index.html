API diff

Diff two OpenAPI documents and flag breaking changes before you ship them.

On this pageWhat counts as breakingGating a pull request on it

Response contracts catch drift in a running API. API Diff catches it one step earlier — in the spec itself, before the change ships. Paste the current (baseline) OpenAPI document and the proposed one into API Diff, and Spi reports every difference, sorted with the changes that break existing clients first. Both JSON and YAML are accepted.

What counts as breaking

A change is *breaking* when it could break a client already calling the old version of the API:

  • An endpoint was removed — a method + path that existed no longer does.
  • A new required input — a required query, header, or path parameter, or a request body that is now required.
  • A parameter became required when it used to be optional.
  • A documented success response was removed — a 2xx the API used to promise is gone.

Everything else is reported but does not break the build: a new endpoint, a new optional parameter, a parameter that relaxed from required to optional, and informational notes such as an API version bump or an added response code.

Gating a pull request on it

The diff is also an API endpoint. Post the two documents to /api/diff/openapi with an API key; it returns 200 when there are no breaking changes and 422 when there are, so a CI step can fail the build on a breaking spec change:

bash
curl -sf -X POST https://apispi.com/api/diff/openapi \
  -H "Authorization: Bearer $SPI_TOKEN" \
  --data-urlencode "old@openapi.main.json" \
  --data-urlencode "new@openapi.branch.json" \
  || echo "Breaking API changes — review before merge."
Every comparison is also saved as a report you can open, share as a read-only link, or compare against a later run. Deep schema comparison (field-level types and enum values) is intentionally left to response contracts, which check them against real traffic.
