API keys and programmatic access

Create named API keys and drive the /api/v1 endpoints from scripts and CI.

On this pageNamed API keysScopesAuthenticating requestsA curl exampleRunning a collection from CIJUnit XML for a CI test reporter

Everything you do in the UI you can also do from a script. The programmatic API lives under /api/v1, is stateless, and is authenticated with a personal API key sent as a bearer token. Manage your keys in Profile.

Named API keys

API keys are named personal credentials — you can hold several at once and name them for where they are used (for example, "CI" or "Local script").

  • Keys are prefixed spi_ so they are recognisable in logs and config.
  • You can create multiple keys per user, up to a fixed limit — if you hit it, revoke one first.
  • A key can be given an optional expiry date, after which it stops working.
  • The full key value is shown exactly once, at creation — copy it then, because it cannot be retrieved later.
  • Keys are revoked, not deleted, so their last-used history and audit trail remain; a revoked key stops working immediately.

Scopes

A key can be restricted to only part of the API. When you create a key, tick the scopes it should be allowed to use:

  • requests — the single-request testers: the proxy and the per-protocol endpoints (mcp, a2a, grpc, mqtt, amqp).
  • collections — running a collection.

Leaving the scopes unchecked grants full access — the key can do everything. A request made with a key outside its scopes is refused with HTTP 403, so a CI key that only runs collections can be scoped to collections and nothing else.

Keys created before scopes existed, and the legacy single key, are unscoped — they keep full access until you replace them with a scoped key.

Authenticating requests

Send the key as a bearer token on every request to /api/v1:

http
Authorization: Bearer spi_your_key_here

These routes are separate from the session-authenticated routes the web app uses: no cookies means no CSRF concern.

A curl example

Send an HTTP request through Spi's guarded proxy:

bash
curl -X POST https://apispi.com/api/v1/proxy \
  -H "Authorization: Bearer spi_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "method": "GET",
    "url": "https://httpbin.org/get"
  }'

Running a collection from CI

Run a collection by id and gate on the status code alone — 200 when every step passed, 422 when any failed:

bash
curl -X POST https://apispi.com/api/v1/collections/{id}/run \
  -H "Authorization: Bearer spi_your_key_here"

JUnit XML for a CI test reporter

Ask for format=junit and the run comes back as JUnit XML instead of JSON — the format GitHub Actions, GitLab, Jenkins, and CircleCI already know how to display. Each step becomes a test case, with the failed assertions in the failure body, so a red pipeline names the step that broke instead of just the run.

bash
curl -sS -X POST https://apispi.com/api/v1/collections/{id}/run \
  -H "Authorization: Bearer spi_your_key_here" \
  -d format=junit -o results.xml
  • A JUnit response is always 200, even when steps failed — a non-2xx would make curl -f discard the very file you want to publish. The failures are inside the document.
  • Gate the build on the test report, or on the X-Spi-Passed response header (true / false). X-Spi-Report-Id gives the saved report for a link back into Spi.
  • A dataset run accepts format=junit too — there, each row is a test case.

A saved run report exports the same way from Reports, or over the API with GET /api/reports/{id}/export?format=junit.

The same key also authenticates the MCP gateway, so an agent driving Spi is scoped to your data.

The /api/v1 surface covers the proxy, the per-protocol testers (MCP, A2A, gRPC, MQTT, AMQP), and collection runs. For the complete, always-current endpoint reference — every field and response shape — see the Developer API page.
